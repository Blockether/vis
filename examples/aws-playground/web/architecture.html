Architecture

Vis as a custom AWS Lambda runtime

The playground runs Vis without a server. Six small functions share one clean container image. Amazon S3 is the database, Amazon EFS holds the repository, and the model provider key stays in one function that a session cannot read.

The parts

VIS_ROLE=front

front

The Function URL. It checks the password, serves the Vis web app and these pages, and relays each API call. It has no network path to the worker.

VIS_ROLE=worker

worker

One active worker holds a lease. It runs the Vis gateway, the sessions, the workflow runs and the extensions. It saves its state in S3 and stops when it is idle.

VIS_ROLE=llm

llm

The only function that reads the provider key. It accepts two calls, the list of models and a chat completion, and only for the models of the stack.

VIS_ROLE=repo

repo

The only function that holds the GitHub deploy key. The key belongs to one repository. It fetches main and pushes fast-forward commits. It never forces a push.

VIS_ROLE=sync

sync

It puts a snapshot of the repository on EFS as a new release and then moves the CURRENT pointer.

VIS_ROLE=app

app

It runs the project for the Studio page: the published release or a work directory of the sessions. It reads EFS and nothing else. Only the front function can invoke it.

ENTRYPOINT

One clean image

The image starts from Amazon Linux. It has no AWS Lambda base image and no Lambda adapter. The embedded Python of Vis is the Lambda runtime: python3 -m playground speaks the Lambda Runtime API.

A call from the browser

  1. The browser sends a call to the Function URL. The front function checks the cookie or the bearer password.
  2. The front function puts the call in the SQS queue. When no worker holds the lease, it starts one.
  3. The worker receives the call and gives it to the Vis gateway on the loopback interface, with its own token.
  4. The worker writes the answer to S3 as numbered parts under relay/. The front function streams the parts to the browser. An event stream of Vis uses the same path.

The worker stops 90 seconds before the Lambda time limit. It drains the gateway, saves the state, releases the lease and starts its successor. A call that arrives in that time waits in the queue.

Each commit is atomic

  • A GitHub webhook and a schedule start the repo function. The webhook carries no data that the stack trusts: the function reads the commit from GitHub.
  • The sync function unpacks the snapshot into a hidden directory, renames it to releases/<sha>, and then replaces CURRENT with one rename.
  • A worker reads CURRENT at its start for the project of its sessions. An active worker keeps that project, and the next worker uses the new commit.
  • Each new workflow run reads CURRENT again and gets its own clone of the newest release in work/<sha>-<run>, so two runs do not change the same files.

Publishing from a session

  1. A session calls playground.publish(message), or a person uses the Publish button of the Sessions page.
  2. The worker commits the work and writes the new commits as a Git bundle to outbox/.
  3. The repo function verifies the bundle, pushes it to main when that is a fast-forward, and to a branch playground/<id> when it is not.
  4. The repo function then fetches the repository, so the new commit becomes the next release.

Workflows on the Vis SDK

  • A workflow is one Python file. @workflow marks the entry and @activity marks each step.
  • ctx.ask(request, Model) calls session.run(response_model=Model) of the Vis SDK. The result is a validated Pydantic object, and the workflow branches on it.
  • ctx.document(name, request) makes the session write a document and attach it with the native attach verb. The SDK reads the files of that turn with session.attachments(turn_id). The file is in the transcript, in S3 and in the run.
  • ctx.receive(key, title) waits for a file from a person. The run gets the status waiting and its process ends, so a waiting run holds no worker. The Factory page shows such a run as a production line.
  • A worker stops before the Lambda time limit and parks the turn that runs. The gateway of the next worker continues that turn. The new run process waits for it and sends no second request.
  • The same workflows run from the Vis web app: the command /workflows of the playground extension opens a panel.

  • The provider key is never in the worker: not in its environment, its files, its role or its network. The gateway talks to a loopback broker, and the broker invokes the llm function.
  • The worker cannot open a connection to the internet. It reaches S3, SQS and Lambda through VPC endpoints, and each endpoint accepts only the resources of this stack. The resolver of the network answers only for AWS names, so DNS queries cannot carry data out.
  • The worker cannot change the release of the next worker. The sync function owns releases/ and CURRENT on EFS, and the worker has another user id.
  • EFS permits a mount only to the sync role, the worker role and the app role, each through its own access point. The app role permits only a read.
  • The code of the project in the Studio runs only in the app function. Its page is in a frame with an opaque origin: it gets no cookie and it can load only its own addresses.
  • A session can push only through the repo function, and that function can write only to one repository and never rewrites history. It refuses a push that changes .github, and GitHub Actions is off for the repository.
  • Outside the network of the stack, the credentials of the worker role permit only a write to the log group of the worker. The bucket keeps each old version of an object for 7 days.
  • Each download of the image has a hash: a digest for its base, a SHA-256 for each file that curl downloads, a hash for each Python package, a Git commit for each extension and a header SHA-256 for each RPM. The image has no Java and no Maven library.
  • The pages set a content security policy that allows only their own scripts, and they never put model text into markup. Each relayed answer of the gateway has a sandbox policy.
  • Each function has a concurrency limit: 50 for front, 5 for worker, 20 for llm, 10 for app, 1 for repo and 1 for sync. A call cannot ask for more output tokens than the limit of the model.
  • The front function compares the password in constant time and sets a signed, HttpOnly, SameSite=Strict cookie that ends after 7 days. A new password is in effect after 5 minutes. The static files are public. The pages, /v1/ and /play/api/ need the password or the cookie.
  • The provider key has no spending limit in this stack. Set a budget for the key at the provider.
  • One stack is for one team that shares its sessions: the code of a session can read and change the data of the other sessions. Give each tenant its own stack.
The limit that you must know. Lambda does not permit the kernel features of the Vis jail (namespaces, seccomp, Landlock). Thus the code of a session runs as the same user as the worker and can read the credentials of the worker role. The design accepts this: the worker role holds no secret and can do only the actions in the table. The isolation is the Firecracker microVM, the role and the network without internet.
